## 4. Firebase and data architecture requirements

### Firebase services

Use:

- Firebase Authentication for account identity and sessions.
- Cloud Firestore for application records.
- Firebase Storage for property images and private documents.
- Firestore Security Rules and Storage Security Rules.
- Firebase App Check where supported and configured.
- Trusted backend code / Cloud Functions for sensitive administrative operations and audit logging where appropriate.

Never put Firebase Admin SDK credentials or service-account private keys in frontend code.

### Authentication requirements

- Real registration and login.
- Logout.
- Persistent Firebase authentication session.
- Password reset if email/password authentication is used.
- Profile management.
- Agent verification workflow.
- Role-based navigation based on trusted authorization data.
- No automatic demo-admin login.
- No LocalStorage value may be treated as proof of identity or admin access.

Use Firebase's authentication state listener. The application must support three states:

1. Authentication is still loading.
2. A real authenticated user exists.
3. No authenticated user exists (`currentUser === null`).

A public visitor must still be able to browse public published properties. Account-required actions should redirect to sign-in or show an authentication prompt.

### Null-safe examples

Do not use `currentUser.uid`, `currentUser.role`, `currentUser.displayName`, `currentUser.phone`, or `currentUser.email` unless `currentUser` has been checked.

Safe basic pattern:

```javascript
if (!currentUser) {
  // Handle signed-out state before accessing currentUser properties.
  return;
}

const userId = currentUser.uid;
```

In components, derive a safe value:

```javascript
const userId = currentUser?.uid ?? null;
const userEmail = currentUser?.email ?? '';
```

Do not use optional chaining as a substitute for authorization. Security must be enforced by Firebase rules and trusted backend code.

### Recommended core collections

The previous discussion identified these collections:

- `users`
- `properties`
- `enquiries`
- `favourites`
- `inspections`
- `confidential_documents`
- `audit_logs`
- `fraud_reports`

The exact field schema must be unified across frontend, Firestore, Storage, and rules. The following are requirements/contracts to validate against the actual project—not a claim that every field already exists.

#### Users

A user profile should associate with the authenticated Firebase UID. Store only fields needed by the product. Authorization must not rely on a user-editable `role` field. Admin/agent privileges should be granted through trusted custom claims or another trusted backend-controlled mechanism.

#### Properties

A property should consistently represent its title, description, listing type, price, currency, country, location, amenities, images, owner/agent ID, status, verification status, and timestamps.

Use Firestore server timestamps for trusted creation/update times. Preserve the document ID as the listing identifier.

#### Enquiries

Requirements discussed:

- The sender/customer, assigned agent, and authorized administrators can read the enquiry as appropriate.
- Creation must validate the sender or permitted guest-submission rules.
- Agents may only manage enquiries assigned to them.
- Status must use `unread`, `contacted`, or `resolved`.
- Ownership and immutable identity fields must not be changed during status updates.

#### Favourites

Requirements discussed:

- A customer can read, create, and delete their own favourites.
- A customer cannot write another user’s favourites.
- Prefer a deterministic document ID or validated ownership fields to prevent duplicate favourites.
- Include a creation timestamp if the app needs sorting/history.

#### Inspections

Requirements discussed:

- Customer, assigned agent, and authorized administrator can read the relevant booking.
- Customers create bookings for themselves.
- Agents can confirm, decline, or reschedule bookings assigned to them.
- Customers can cancel their own eligible bookings.
- Restrict updates to the exact fields permitted for each action. Do not allow a status-only action to alter ownership, property ID, customer ID, or agent ID.

#### Confidential documents

Title deeds, identity evidence, and other confidential documents must not be publicly readable. Validate document ownership, path, content type, size, and authorized access in Storage and Firestore. Do not assume Firestore rules automatically secure Storage files.

#### Audit logs

Do not let arbitrary clients create trusted audit entries. Generate important audit records from trusted backend code (for example, Cloud Functions) so a user cannot fabricate an administrative history.

#### Fraud reports

Protect reports from unauthorized reading and abuse. Validate required fields, prevent users from reading other users’ private reports, and consider rate limiting or abuse controls in trusted backend logic.

## 5. Firestore security rules: design decisions and issues identified

The user previously pasted several versions of Firestore Rules beginning with:

```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
```

The code fragments and review context included helpers such as:

- `isAuthenticated()` — checks `request.auth != null`.
- `isOwner(userId)` — checks the authenticated UID matches the target user ID.
- `isAdmin()` — checks a trusted admin custom claim, previously shown as `request.auth.token.admin == true`.
- `isAgent()` — an agent authorization helper was part of the discussed role system.
- `isValidString(...)` — a validation helper appeared in one of the pasted versions.

The full original rules file is not preserved in the available context, so it cannot be reprinted verbatim here.

### Earlier collection-level policy discussed

- `users`: users can access their own private profile; administrators have authorized management access; agent public profiles may be readable as intended; arbitrary authenticated users should not be able to read all private user documents.
- `properties`: only published listings are public by default; agents can create their own draft/pending-review listings; agents cannot self-publish or change verification; administrators review and publish/reject.
- `enquiries`: access is limited to the sender/customer, assigned agent, and administrators; creation and updates require validation.
- `favourites`: owner-only access.
- `inspections`: access limited to customer, assigned agent, and administrators; updates constrained by actor and action.
- `confidential_documents`: strict, private access.
- `audit_logs`: trusted write path; private authorized read path.
- `fraud_reports`: protected reporting and review workflow.

### Security weaknesses found in generated versions

The review identified these risks in earlier generated rules/code:

1. Some user rules allowed every authenticated user to read user documents too broadly.
2. Some user updates lacked a sufficiently restrictive field whitelist.
3. A user could potentially create their own profile with arbitrary role/privilege fields unless explicitly prohibited.
4. An agent property update rule was too broad: the agent could potentially change sensitive fields beyond the permitted listing fields.
5. Some property updates were unrestricted for an owning agent or admin instead of validating changed fields and state transitions.
6. Inspection updates could modify too many fields instead of only the fields allowed for cancellation, confirmation, decline, or rescheduling.
7. Enquiry status changes needed strict enum validation and immutable ownership fields.
8. Confidential-document metadata needed stricter validation.
9. Arbitrary client-created audit logs are not trustworthy.
10. Fraud-report creation needs validation and anti-abuse controls.
11. A favourites rule using `request.resource.data` for all read/write operations could fail for reads or deletes because that object is not available in the same way for every operation.

Do not fix these issues by opening access broadly. Use restrictive authorization and validation.

### Critical Firestore query rule

**Firestore Security Rules are not filters.** A query must be constructed so its potential result set satisfies the rule.

Public property browsing should explicitly request published records, for example:

```javascript
query(
  collection(db, "properties"),
  where("status", "==", "published")
);
```

Agent queries should explicitly restrict records to the authenticated agent’s UID, for example:

```javascript
query(
  collection(db, "properties"),
  where("agentId", "==", auth.currentUser.uid)
);
```

The exact field names must match the final database schema.

If the public Explore page is allowed to include sold/rented listings, the security rules must intentionally permit those public-safe documents. Do not expose sensitive fields through documents merely to make this filter work. Firestore rules do not provide field-by-field redaction of a returned document; consider separating public listing data from private operational data.
